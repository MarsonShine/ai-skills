# Output template

If there are information gaps, put these two sections first and omit them only when unnecessary:

## 默认假设

- 只列低风险、可工程化补齐的内容
- 每条末尾标注“（默认假设）”

## 待确认问题

- 只列真正影响范围、成本、边界、权限、风控、计费或一致性的缺口
- 高风险问题补一句“风险与影响”

Then use this structure:

## 1. 需求理解

- 用 1~3 段话总结业务目标
- 点明要解决的核心问题
- 点明本次方案要落地的关键能力

## 2. 业务范围

- 明确包含项
- 明确不包含项
- 边界条件、前置依赖、触发条件

## 3. 核心业务流程

- 按步骤写正常流程
- 补异常流程和边界流程
- 体现状态变化、外部交互、失败分支、人工介入点

## 4. 角色与权限

- 业务用户、运营/审核、管理员、系统角色、第三方角色
- 每个角色说明“能做什么 / 不能做什么 / 能看到什么”
- 涉及越权风险时说明隔离方式

## 5. 业务规则

- 输入校验
- 业务前置条件
- 状态流转与禁止流转
- 幂等、防重、并发、权限、一致性规则

## 6. 数据模型建议

- 拆核心实体
- 每个实体给关键字段、字段含义、类型建议、是否必填、默认值
- 状态字段给状态枚举、含义、允许流转
- 必要时补唯一键、索引、软删除、版本号、审计字段

## 7. 接口/功能拆分建议

- 按业务动作拆，不要只写 CRUD
- 每个模块写输入、输出、前置校验、核心副作用
- 适合时补 API 字段或事件字段

## 8. 异常处理与容错

- 枚举可能错误场景
- 说明拦截、重试、回滚、补偿、降级、人工介入
- 区分用户可见错误、系统内部错误、外部依赖错误

## 9. 日志、审计与监控

- 业务日志、技术日志、审计日志分别记录什么
- 哪些操作必须审计
- 监控哪些核心指标、失败指标、时延指标、积压指标
- 说明告警触发条件

## 10. 测试建议

- 单元测试点
- 集成测试点
- 边界测试点
- 异常测试点
- 涉及并发、重试、补偿、权限时单独列专项测试

## 11. 实现优先级

- 必须先做的能力
- 第二阶段优化项
- 推荐开发顺序和排序原因

## Depth rules

### 流程

不要只写“提交后系统处理并返回结果”。至少说明：

- 谁发起
- 系统校验什么
- 生成或更新什么实体
- 状态如何变化
- 是否调用外部系统
- 失败后怎么处理
- 是否需要通知、回调、补偿或人工处理

### 业务规则

优先覆盖：

- 入参合法性
- 业务前置条件
- 状态前置条件
- 唯一性与防重复
- 并发冲突处理
- 权限边界
- 数据一致性
- 时间窗口 / 频率 / 额度限制
- 外部依赖失败兜底

### 数据模型

至少说明：

- 实体名称
- 主键或业务唯一键
- 核心字段
- 状态字段
- 审计字段
- 建议索引

流程型业务优先拆成“主单 + 流转记录 + 审计/操作记录”。

### 接口/功能拆分

优先按业务动作拆：

- 创建
- 提交
- 审核
- 取消
- 查询列表
- 查询详情
- 重试
- 导出
- 回调接收
- 配置管理

天然异步的业务要显式说明消息、任务或回调处理。

## Delivery self-check

交付前检查：

1. 是否指出核心问题，而不是只复述背景
2. 是否明确范围边界与不包含项
3. 是否同时覆盖正常、异常、边界流程
4. 是否补齐角色、权限、状态、规则、数据模型、接口、监控、测试
5. 是否把默认假设与待确认问题显式标出
6. 是否具体到代码智能体可以直接继续开发
