# 图片质量

## 先说结论

微信**无法绕过**，它会在入库时重新编码。所谓「无损上传」不是骗服务端，而是让输入落进它不做有损处理的区间：

| 输入 | 结果 |
|---|---|
| **PNG**，高 ≤29999px | 尺寸与画质都保留，透明通道不会被转 JPEG → **实测无损** |
| **JPEG**，宽 ≤1280 且高 ≤16383 | 尺寸不变，但仍有二次质量压缩，**有损** |
| **JPEG**，超尺寸 | 等比缩小，尺寸直接降 |
| 高 >29999px | 上传直接失败 |

所以：

- **截图、图表、设计稿、带文字的图** → 用 PNG，是真无损。
- **摄影照片** → 做不到。已经过一次有损重编码，细节回不来。

## 真正的瓶颈是 1MB

正文图走 `media/uploadimg`，单图硬上限 **1 MB**。
一张 3000×2000 的照片存成 PNG 常有 8–15 MB，根本传不上去。

这就是为什么「无损」在实践中更多是**内容型图片**的福利：
图表、截图、UI 稿通常几百 KB，天然在 1MB 内；照片不在。

封面走 `material/add_material`，上限 **10 MB**，所以封面比正文容易做到无损。

## 四档策略

| 档位 | 行为 | 适用 |
|---|---|---|
| `lossless` | PNG 原样；>1MB 走无损瘦身（pngquant 或调色板量化）；JPEG 不缩不降质 | 设计稿、图表、截图 |
| `high` | 仅在超 1MB 时缩到 1280 宽，质量 92 | 摄影图、要清晰的人像 |
| `balanced`（默认） | 超 1MB 才缩到 1280，再从 95 往下**二分**找能塞进 1MB 的最高质量 | 日常 |
| `small` | 强制缩到 900 宽，质量 70 | 图多省流量 |

### 顺序铁律

**先定尺寸 → 再定格式 → 最后才谈质量。**

顺序反了，细节在第一步就丢了。这也是「压完还是糊」的最常见原因——先降质再缩尺寸，等于把两次损失叠在一起。

### 已经够小就不要动

原图 ≤1MB 时，除非明确要 `small`，一律**保持原样不重编码**。

把一张 200KB 的图重编码一遍，不会让读者看得更清楚，只会让文字边缘和线条变脏。判据是 1MB 硬上限，不是某个宽度阈值。

（原型里有过这个错误：1400px 宽、7KB 的图表被缩到 1280px，纯粹是自损。）

### PNG 优先无损瘦身

超 1MB 的 PNG 先尝试无损压缩，成功了就还是 PNG：

1. 装了 `pngquant` → `--quality 100` 无损量化。
2. 没装 → 用 PIL 检查颜色数，≤256 色时转调色板（真无损）。
3. 都不行 → `lossless` 档直接报错，`high`/`balanced` 才降级到 JPEG。

**为什么不直接转 JPEG**：图表的价值全在文字和线条上，JPEG 的块效应会把它们糊掉。

## 不靠承诺，靠证据

上传后把图从 CDN 下载回来，用 PIL 量像素尺寸和字节数：

```json
{
  "src_px": "1080x720",
  "cdn_px": "1080x720",
  "src_bytes": 812000,
  "cdn_bytes": 818000,
  "lossless": true
}
```

判定：
- 尺寸一致 **且** 字节数 ≥ 源文件 90% → `lossless: true`
- 尺寸变了 → `loss_reason: "服务端改了尺寸：1080x720 → 800x533"`
- 尺寸没变但字节明显缩水 → `loss_reason: "尺寸未变但字节明显缩小，服务端做过重压缩"`

**附带好处**：微信以后改规则，核验结果会立刻暴露，不用等读者说「图怎么糊了」。

**为什么策略里不写死 1080/1280 常量**：社区里「宽度必须 1080」和实测「1280」两个阈值并存（1080 更像是后台编辑器路径的值）。一切以回读像素为准。

## 预演：`qc` 子命令

不上传也能知道每张图会发生什么：

```bash
python3 scripts/wx_publish.py qc --images ./photos --quality lossless
```

返回每张图的 `src_px / out_px / src_bytes / out_bytes / action / lossless / reason`。

`action` 取值：

| action | 含义 |
|---|---|
| `keep` | 原样使用 |
| `lossless_shrink` | 无损瘦身后使用，仍是 PNG |
| `resize` / `resize+reencode` | 缩了尺寸 |
| `reencode` | 尺寸不变，重编码 |
| `blocked` | 无法在不降质前提下处理 |

`blocked` 时 CLI 以 **exit 7** 退出，并给三个选项：缩到 1280 宽 / 改 `high` 档 / 换图。**绝不偷偷降质。**

## 常见误区

| 误区 | 事实 |
|---|---|
| 「传原图微信会保留原图」 | 不会。服务端必重编码。 |
| 「转 PNG 就无损」 | 只对 ≤1MB 的图成立。超了照样要降。 |
| 「宽度 1080 是硬性要求」 | 不是硬性限制。正文区最大宽 677px，宽度更多影响清晰度观感。 |
| 「webp 更小，用它」 | 正文图只收 jpg/png。webp 会被转码，反而更差。 |
| 「先降质量再缩尺寸比较快」 | 这是最糟的顺序，损失叠加。 |
| 「图多一点没关系」 | 一篇文章十几张 1MB 图，读者流量和加载都会难受，`small` 档有意义。 |
